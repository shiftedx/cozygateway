# Install cozygateway (agent playbook)

**You are an AI agent. This document is your instruction set, not documentation for a human.**
The human who handed you this URL wants cozygateway running beside the Hermes install they already
have, so their phone can talk to their bots. Everything below is imperative. Run the steps in
order. Each step ends with a **Check** command and the **Expect** line that command must produce.
If a check fails, stop, read the Troubleshooting table at the bottom, fix, and re-run that step.
Do not continue past a failed check.

Rules for you, the installing agent:

- **Every command you run starts in a fresh shell.** Nothing survives between commands: not a
  variable, not a `cd`, not an `export`. So this playbook never asks you to carry a value in your
  head or in `$SOMETHING` from one step to the next. Every value lives in a file, and every command
  that needs one reads it on the spot. If you ever find yourself about to type a `$VAR` that some
  earlier step set, you have lost the thread: go back and read it from the file instead.
- Never invent a value. Every value you need is either generated by a command here, read out of a
  file here, or asked of the human in Step 0.
- Never print the human's password back into a shared channel, and never pass it as a command-line
  argument: argv is visible in `ps` to every user on the machine. The commands below pipe it on
  stdin. Show the human the **pairing code** and nothing else secret.
- Everything here is idempotent. Re-running a step is always safe.
- The human's Hermes install is theirs. You edit exactly one file of theirs, `config.yaml`, you
  back it up first, and you tell them the merge reserializes the file (see Step 3).

`scripts/agent-install.sh` owns the stateful half of this install, end to end: it generates the
password, hashes it, merges `config.yaml`, writes the gateway config and `.env`, starts things and
mints a pairing code. It writes everything a later step needs into two mode-600 files:

    ~/cozygateway/local/install-env.sh              ports, hosts, runtime, paths (source it)
    ~/cozygateway/local/dashboard-credentials.txt   username, password, password_hash

Steps 4 through 9 read those files. That is the whole state-passing mechanism. If the script cannot
run on this machine, Appendix A does the same work by hand, writing the same two files.

## How push works

The installer configures `https://push.cozylabs.ai` without asking a new question. The
gateway encrypts every notification end to end before sending it. The hosted relay sees
only an opaque push ID, ciphertext, optional category and collapse ID, and the source IP
transiently for rate limiting. It never sees message content or device identity. Set
`COZYGATEWAY_PUSH_RELAY_URL` before running the installer to persist a different relay URL.

A self-hosted relay cannot push to the store app because APNs keys are scoped to the
publisher team. Developers signing their own app with their own Apple team can instead
use the Compose `local-push` profile described in `docs/self-host-docker.md`.

## Step 0. Decide the shape, with the human

Ask, and record the answers. Do not guess.

0. **Docker, Node checkout, or prebuilt bundle?** If the human answering is not technical, and
   just wants cozygateway running with the least fuss, stop here and hand them the one-liner
   instead of this playbook: `curl -fsSL https://cozylabs.ai/install.sh | bash` (see
   `docs/install-service.md`). It needs Node 24+, no Docker and no git, and it registers both the
   gateway and the Hermes dashboard as login services on its own. This playbook is for the Docker
   path, a Node checkout you build, or a prebuilt bundle (`--bundle PATH`) you already have.
1. **Which machine runs the gateway?** It must be the same machine as Hermes, or one that can
   reach Hermes over the network. The phone must be able to reach the gateway (same LAN, VPN, or a
   tunnel; see Step 8).
2. **Docker or Node?** Docker is the reference path and the one to prefer.
3. **Which Hermes profiles are bots?** Every other profile (the `default` profile, service or
   automation profiles) goes into `hiddenProfiles` and stays off the roster.
4. **Does the dashboard have to leave loopback?** The installer binds the Hermes dashboard to
   `127.0.0.1` by default, which is right when Hermes and the gateway are the same machine and the
   gateway runs under Node. Two cases need more:
   - Gateway in a container on **Docker Desktop** (macOS or Windows): a container cannot reach the
     host's loopback, and the docker bridge address lives inside Docker's VM, so the dashboard has
     to bind `0.0.0.0`.
   - Gateway on a **different machine** from Hermes: same answer.

   Binding `0.0.0.0` publishes the human's entire Hermes dashboard (config, API keys, sessions) to
   the LAN over plaintext HTTP, protected only by the basic-auth password from Step 3. **Say that
   out loud to the human and get their agreement** before passing `--expose-dashboard-lan`. On an
   untrusted network, prefer Tailscale or a tunnel over exposing it. On Linux the installer finds
   the docker bridge address by itself and needs none of this.

Write the answers down before continuing; Step 3 turns them into flags.

## Step 1. Preflight

Read-only. All four must pass before you touch anything.

**1a. Hermes is installed and new enough.** Bot Mode arrived in 0.20.2.

    hermes --version

**Check:** the version in the first line is `0.20.2` or higher.
**Expect:** several lines, the first shaped like
`Hermes Agent v0.20.4 (2026.8.18) · upstream acc614e7`. Read the version out of the `v0.20.4`
field. The `(2026.8.18)` is a build date, not a version: do not compare against it. If
`hermes: command not found`, stop: the human has to install Hermes first, and this playbook has
nothing to attach to.

**1b. A container runtime, or Node.**

    docker compose version || node --version

**Expect:** either `Docker Compose version v2.x.x` or newer (take the Docker path), or `v24.x.x`
or higher (take the Node path). **Node 24 is a hard requirement**, in the `engines` field of every
package and in the installer, which refuses to run on anything older. If Docker is present, prefer
it. If Docker is installed but its daemon is not running, `docker info` says so; start Docker
Desktop or `dockerd` before Step 3. (`scripts/agent-install.sh --dry-run` still prints its whole
plan with the daemon down, so you can read the plan first either way.)

**1c. The Hermes home.**

    ls -la "${HERMES_HOME:-$HOME/.hermes}/config.yaml"

**Expect:** the file exists, and is a regular file rather than a symlink (an `l` at the start of
the mode string). If it does not exist, the human has never run Hermes on this machine;
`HERMES_HOME` may point elsewhere. Ask before assuming. If it is a symlink, the installer will
refuse to write through it, and rightly: point `--hermes-home` at the directory holding the real
file instead.

**1d. The interpreter Hermes runs under.** Step 3 needs it, because only it can import the bundled
password hasher and PyYAML. This is the step most likely to go wrong, so prove it rather than
guessing at it.

    hermes --version | sed -n 's/^Install directory: *//p'

**Expect:** a path, for example `/Users/you/.hermes/hermes-agent`. The interpreter is
`<that path>/venv/bin/python3` (some installs use `.venv`). Prove it imports both modules:

    "$(hermes --version | sed -n 's/^Install directory: *//p')/venv/bin/python3" -c \
      'import yaml; from plugins.dashboard_auth.basic import hash_password; print("ok")'

**Expect:** `ok`.

Do **not** take the interpreter from the `hermes` shebang. On the reference install `hermes` is a
bash wrapper (`#!/usr/bin/env bash`) whose last line is `exec "<install dir>/venv/bin/hermes"`, so
the shebang names a shell, and the plain `python3` on `PATH` that a shebang-based guess falls back
to has no `yaml` module at all. If `hermes --version` prints no install directory, read the
wrapper (`cat "$(command -v hermes)"`) and take the directory from its `exec` line; the python sits
beside that binary.

If neither works, ask the human which environment Hermes runs in. Do not fall back to a python that
cannot import `yaml`: the installer refuses that python by design, and so should you.

The installer resolves this by itself and prints which interpreter it chose. Only when it chooses
wrong do you need to override it, which you do on its own command line:

    COZYGATEWAY_HERMES_PY=/path/to/venv/bin/python3 bash scripts/agent-install.sh ...

## Step 2. Get the gateway

    git clone https://github.com/shiftedx/cozygateway.git ~/cozygateway

If the directory already exists, update instead of cloning:

    git -C ~/cozygateway pull --ff-only

**Check:**

    ls ~/cozygateway/docker-compose.yml ~/cozygateway/docker/agent-install.override.yml

**Expect:** both paths listed, no `No such file or directory`. If the override file is missing, the
checkout predates this playbook; pull `main`.

Everything this install generates (the gateway config, the SQLite database, logs, the recorded
dashboard credential, the state file this playbook reads) goes in `~/cozygateway/local/`, which
ships with a `.gitignore` that ignores its own contents. Nothing you write there can be committed
by accident.

**Check:** `git -C ~/cozygateway status --porcelain local/`
**Expect:** no output at all.

## Step 3. Run the installer (the stateful half)

One command does the whole stateful half: generate the dashboard password, hash it with the hasher
Hermes bundles, merge `basic_auth` and the approval pin into the human's `config.yaml` (after a
timestamped backup), start the dashboard, write the gateway config and `.env`, start the gateway, and mint a pairing
code. Read the plan first if you like:

    cd ~/cozygateway && bash scripts/agent-install.sh --dry-run

Then run it, with the flags from Step 0:

    cd ~/cozygateway && bash scripts/agent-install.sh --hidden-profiles default

Flags you may need, from the Step 0 answers:

| Answer | Flag |
| --- | --- |
| Non-bot Hermes profiles | `--hidden-profiles default,ops,scratch` |
| Node instead of Docker | `--runtime node` |
| Dashboard must leave loopback (Docker Desktop, or a remote gateway) | `--expose-dashboard-lan` |
| A specific narrower bind address | `--dashboard-host 172.17.0.1` |
| Port 8787 or 9119 already in use | `--gateway-port 9000` / `--dashboard-port 9120` |
| Hermes home somewhere else | `--hermes-home /srv/hermes` |
| A dashboard password the human already has | none, see below |
| A prebuilt single-file gateway instead of a clone/build | `--bundle /path/to/cozygateway.mjs` (implies `--runtime bundle`; needs node 24+) |
| Run the gateway (and dashboard) as an OS-supervised login service instead of `nohup` | `--service` (launchd on macOS, systemd `--user` on Linux; not for `--runtime docker`, which already supervises itself) |
| Remove service units this script installed | `--uninstall-service` (stops and removes both units, prints what went, needs neither hermes nor docker) |

The installer has a `--password` flag and you should not use it. A password on a command line is
visible in `ps` to every user on the machine and lands in shell history. If the human already has a
dashboard password, or insists on choosing one, write it into the credentials file yourself and let
the installer pick it up from there: run Appendix A steps A1 to A3 (substituting their value for
the generated one in A2), then run the installer normally. It reuses a recorded password and its
recorded hash and re-hashes nothing.

**What it writes, and nothing else:**

- `~/cozygateway/local/*`, all mode 600 and git-ignored.
- `~/cozygateway/.env`, **merged key by key**. It owns exactly three keys
  (`COZYGATEWAY_ATTACH_TOKEN`, `COZYGATEWAY_HERMES_PASSWORD`, `COZYGATEWAY_PORT`) and preserves
  every other line byte for byte, including the `APNS_*` and `COZY_RELAY_PORT` keys the push relay
  reads from the same file.
- `<hermes home>/config.yaml`, **merged** into the existing `dashboard:` and `approvals:` blocks
  after a timestamped backup. Two keys, and nothing else: `dashboard.basic_auth` (the bridge
  credential) and `approvals.mode: manual` (see below). `approvals.timeout` is the human's number
  and is left exactly as it is. It refuses outright, writing nothing and leaving no backup, if that
  file already has two top-level `dashboard:` keys, is a symlink, or sets
  `security.approval.transport` (see below).

**Tell the human this**, because it is theirs and they cannot see it from the log: the merge is
done by the YAML parser, which reserializes the whole file. **Comments and anchors do not survive**,
and unrelated top-level sections come back reformatted. The values are all preserved and the
original is in the `config.yaml.bak-agent-install-*` file beside it.

**Why `approvals.mode: manual` is pinned, and why the installer will not merge over an approval
transport.** Both are about the phone's approve/deny surface (cozygateway#19), and both are
invisible from the outside: the gateway advertises the capability either way and simply never sends
a frame, so a misconfigured box looks like a broken app rather than a missing setting.

- `approvals.mode` defaults to `smart` on Hermes 0.20.x: an aux-LLM guardian that decides for
  itself, and on an APPROVE decision the tool just runs with **no event emitted at all**. The phone
  is asked sometimes and not others. `manual` is the only mode under which every approval reaches a
  human, so the installer pins it, merging into whatever `approvals:` block is already there.
- `security.approval.transport`, if it is set to anything but `builtin`, routes the whole approval
  prompt to a registered plugin **before** the dashboard-WebSocket branch is reached. The bridge
  then never sees an approval at all. Removing somebody's security setting behind their back is not
  the installer's call, so it stops, names the key, and leaves the file untouched. Fix it by hand
  (or pass `--skip-dashboard` and own `config.yaml` yourself) and re-run.

If you deliberately run with `--skip-dashboard`, `config.yaml` is not touched at all and **both of
these are yours to get right**, or mobile approve/deny will be silently dead.

**A third key, same shape of hazard: `display.tool_progress`.** It gates the live tool-step chips a
bot chat shows while a turn runs (cozygateway#60, ext-bots capability 12). It defaults to `all`, so
the ordinary install needs nothing and the installer does not touch it. Set to `off`, Hermes stops
emitting `tool.start` and `tool.complete` at the source, the gateway sends no `bot_tool_activity`
frame, and a long turn shows plain "thinking" again with nothing anywhere saying why. If chips are
missing on an otherwise healthy box, check this key before anything else.

**Check:**

    ls -l ~/cozygateway/local/install-env.sh ~/cozygateway/local/dashboard-credentials.txt

**Expect:** both files, both `-rw-------`. Every remaining step reads them. If they are missing, the
installer stopped early: read its last `FAIL` line, which names the fix.

**Check:** `. ~/cozygateway/local/install-env.sh && echo "$COZY_RUNTIME $COZY_GATEWAY_PORT $COZY_DASHBOARD_PORT $COZY_DASHBOARD_HOST"`
**Expect:** four values, matching the Step 0 answers, for example `docker 8787 9119 0.0.0.0`.

## Step 4. Verify the dashboard credential

The bridge does not use a loopback token. It logs in to the Hermes dashboard with an ordinary
username and password, exactly like a browser, and mints a fresh single-use WebSocket ticket for
every connect. Hermes fails **closed** on any non-loopback bind with no auth provider registered,
so this credential is not optional.

**4a. The merged block is there, exactly once, with no plaintext password.**

    . ~/cozygateway/local/install-env.sh && \
      grep -c '^dashboard:' "$COZY_HERMES_HOME/config.yaml" && \
      "$COZY_HERMES_PY" -c "import yaml,sys; print(sorted(yaml.safe_load(open(sys.argv[1]))['dashboard']['basic_auth']))" \
        "$COZY_HERMES_HOME/config.yaml"

**Expect:** `1`, then `['password_hash', 'username']`. A `password` key in that list is a plaintext
credential at rest; remove it. A count of `2` means the file has duplicate `dashboard:` keys, which
the installer refuses to touch: fold them into one block by hand and re-run Step 3. Note that this
count alone proves nothing about a file that was already broken before the install, which is why
the installer checks for duplicates before it writes rather than after.

**4b. The credential actually logs in.** This is the check that matters, and the only one that
proves the running dashboard loaded the merged config rather than an older one it started with.
It is byte for byte the request the bridge makes
(`packages/gateway/src/hermes-bridge/client.ts`), and the password goes over stdin, never argv:

    . ~/cozygateway/local/install-env.sh && \
      "$COZY_HERMES_PY" -c 'import json,sys; d=dict(l.split("=",1) for l in open(sys.argv[1]).read().splitlines() if "=" in l); print(json.dumps({"provider":"basic","username":d["username"],"password":d["password"],"next":"/"}))' \
        "$COZY_CRED_FILE" | \
      curl -s -o /dev/null -w '%{http_code}\n' -X POST \
        "http://127.0.0.1:$COZY_DASHBOARD_PORT/auth/password-login" \
        -H 'content-type: application/json' --data-binary @-

**Expect:** `200`. Nothing else is a pass here.

- `401` means the running dashboard does not have this credential. The usual cause is a dashboard
  that was **already running before Step 3**: Hermes runs one machine-level server by default, so
  that process is still holding the config it read at startup and never saw the merge. Restart it:
  `hermes dashboard --stop`, then re-run Step 3. (`hermes dashboard --status` lists the running
  servers.) The installer does this restart itself, so a 401 here means it was skipped or it
  failed.
- `404` means the dashboard has no auth provider under the name `basic`; see Troubleshooting.
- `000` means nothing is listening: read `~/cozygateway/local/hermes-dashboard.log`.

Do not accept a `200` from `/api/health` as a substitute for this check. `/api/health` answers 200
before authentication is configured and 401 after, so it proves a process is listening and nothing
about which credential it loaded.

---

**4c. The approval pin landed, and nothing diverts approvals off the WebSocket.**

    . ~/cozygateway/local/install-env.sh && \
      "$COZY_HERMES_PY" -c "import yaml,sys; c=yaml.safe_load(open(sys.argv[1])); print((c.get('approvals') or {}).get('mode'), ((c.get('security') or {}).get('approval') or {}).get('transport'))" \
        "$COZY_HERMES_HOME/config.yaml"

**Expect:** `manual None`. Anything else and the phone's approve/deny surface is silently dead:
`smart` lets an aux LLM approve a call with no event emitted, and a non-`builtin` transport routes
the prompt to a plugin before the WebSocket branch. See Step 3 for why, and fix it there rather
than here.

## Step 5. Verify the gateway config and `.env`

**5a. The config file.** It names the environment VARIABLE that holds the password; it never holds
the password itself.

    . ~/cozygateway/local/install-env.sh && \
      "$COZY_HERMES_PY" -c "import json,sys; c=json.load(open(sys.argv[1])); print(c['hermes']['authMode'], len(c['agents']), c['port'], c['hermes']['url'], c['hermes']['hiddenProfiles'])" \
        "$COZY_CONFIG_JSON"

**Expect:** `password 0 8787 ws://host.docker.internal:9119/api/ws ['default']` on the Docker path,
with `ws://127.0.0.1:9119/api/ws` on the Node path, the port matching `COZY_GATEWAY_PORT`, and the
hidden profiles matching the Step 0 answers.

`"agents": []` is valid and correct here. A gateway must serve something, and the `hermes` block is
a complete surface on its own: a bots-only gateway carries no attach agents at all. A config with
neither refuses to start and says so.

**5b. `.env` reached the container intact.** Docker path only.

    . ~/cozygateway/local/install-env.sh && cd "$COZY_GATEWAY_DIR" && \
      docker compose -f docker-compose.yml -f docker/agent-install.override.yml config | \
      grep -E 'COZYGATEWAY_(PORT|HERMES_PASSWORD)|published'

**Expect:** `COZYGATEWAY_PORT` and the published port both equal to `COZY_GATEWAY_PORT`, and a
`COZYGATEWAY_HERMES_PASSWORD` whose length matches the recorded one. Compare the length rather than
eyeballing the value:

    . ~/cozygateway/local/install-env.sh && cd "$COZY_GATEWAY_DIR" && \
      echo "recorded: $(sed -n 's/^password=//p' "$COZY_CRED_FILE" | head -1 | wc -c)" && \
      echo "resolved: $(docker compose -f docker-compose.yml -f docker/agent-install.override.yml config | sed -n 's/.*COZYGATEWAY_HERMES_PASSWORD: //p' | tr -d '"' | wc -c)"

**Expect:** the two counts match.

> **WARNING.** Compose interpolates every value in `.env`. A literal `$` must be written `$$`. We
> lost a scrypt hash this way: it arrived at the container truncated to 36 characters at its first
> `$`, and the only symptom was a 401 on the bridge login that looked exactly like a wrong
> password. The installer generates a `$`-free password, so this cannot bite you unless the human
> supplied their own.

**5c. Nothing else in `.env` was disturbed.** Only if the human had other keys there (relay APNs
settings, `COZY_RELAY_PORT`):

    grep -vE '^(COZYGATEWAY_ATTACH_TOKEN|COZYGATEWAY_HERMES_PASSWORD|COZYGATEWAY_PORT)=' ~/cozygateway/.env

**Expect:** every line the human had before, unchanged. The installer owns three keys and merges;
it does not rewrite the file.

## Step 6. Verify the gateway is serving the bots surface

**6a. The capability.**

    . ~/cozygateway/local/install-env.sh && \
      curl -s -w '\n%{http_code}\n' "http://127.0.0.1:$COZY_GATEWAY_PORT/health"

**Expect:** `200`, and JSON carrying `"contract":"v1"` and a capabilities map that includes
`"com.cozylabs.bots"` with an integer version (3 or higher). That key is the proof the bridge is
configured: a gateway with no `hermes` block omits it entirely and registers no `/bots` routes.
If it is absent, the config file did not load; check the mount path and re-read Step 5.

`/health` is the only unauthenticated endpoint on the gateway. Everything else, `/bots` included,
requires a device token.

**Photos to bots (capability 9) need nothing installed, but they do need a bot that can see.** The
route works on any Hermes at the 0.20.2 floor and adds no install step, no credential and no config
change. Whether the bot receives PIXELS rather than a text description is decided by its own profile:
leave `agent.image_input_mode` at its default `auto` and point the bot at a vision-capable model. Two
caveats worth knowing before someone reports a bug: a profile running
`model.openai_runtime: codex_app_server` is forced to the text path whatever its model, and a
non-vision main model routes to text and needs `auxiliary.vision` configured to be useful at all. The
gateway cannot observe either decision, so neither shows up as an error; the bot simply describes
instead of looking.

**6b. The bridge actually logged in.**

    . ~/cozygateway/local/install-env.sh && cd "$COZY_GATEWAY_DIR" && \
      docker compose -f docker-compose.yml -f docker/agent-install.override.yml logs gateway | \
      grep -i 'hermes dashboard'

(Node path: `. ~/cozygateway/local/install-env.sh && grep -i 'hermes dashboard' "$COZY_GW_LOG"`.)

**Expect:** `logged in to the hermes dashboard; session established`. Anything else, in particular a
401 or a message naming the auth provider it tried, means the credential path is wrong: go back to
Step 4b, then to Troubleshooting.

## Step 7. Verify the roster, with a real device token

`/bots` sits behind the device-token middleware (`packages/gateway/src/http.ts`). An
unauthenticated `curl` returns `401` with an error body no matter how healthy the bridge is, and a
check that just prints that body and shrugs would pass on a completely broken install. So pair a
throwaway device, call `/bots` with its token, assert the status code, and revoke the device again.
The installer already ran exactly this check and printed its result; run it yourself to confirm, or
after any change.

Docker path (Node path: replace the `docker compose ... exec -T gateway node dist/cli.js` prefix
with `node packages/gateway/dist/cli.js` and `--config /app/cozygateway.config.json` with
`--config "$COZY_CONFIG_JSON"`):

```sh
. ~/cozygateway/local/install-env.sh && cd "$COZY_GATEWAY_DIR" && \
CODE="$(docker compose -f docker-compose.yml -f docker/agent-install.override.yml \
  exec -T gateway node dist/cli.js pair --config /app/cozygateway.config.json \
  | head -1 | sed -n 's/.*"setupCode":"\([^"]*\)".*/\1/p')" && \
RESP="$(printf '{"setupCode":"%s","deviceName":"install-check"}' "$CODE" | \
  curl -sS -X POST "http://127.0.0.1:$COZY_GATEWAY_PORT/pair" \
    -H 'content-type: application/json' --data-binary @-)" && \
TOKEN="$(printf '%s' "$RESP" | sed -n 's/.*"deviceToken":"\([^"]*\)".*/\1/p')" && \
DEV="$(printf '%s' "$RESP" | sed -n 's/.*"device":{"id":"\([^"]*\)".*/\1/p')" && \
curl -s -w 'bots:%{http_code}\n' -H "authorization: Bearer $TOKEN" \
  "http://127.0.0.1:$COZY_GATEWAY_PORT/bots" && \
curl -s -o /dev/null -w 'revoked:%{http_code}\n' -X DELETE \
  -H "authorization: Bearer $TOKEN" "http://127.0.0.1:$COZY_GATEWAY_PORT/devices/$DEV"
```

That is one command on purpose: the setup code, the token and the device id never leave the shell
that made them.

**Expect:** a JSON object with a `bots` array (a fresh gateway answers `{"bots":[],...,"stale":true}` on the first read, which is fine), then `bots:200`, then `revoked:200`.

- `bots:401` means the token was not sent or not accepted; re-run the whole block.
- `bots:200` with `[]` is a **real pass**: the human has no visible bot profiles yet, or they are
  all in `hiddenProfiles`. Report it as an empty roster, not as a failure, and check
  `hiddenProfiles` against the Step 0 answers. It is a pass only because the `200` was asserted;
  an empty body with no status code proves nothing.
- `revoked:` anything other than `200` means the throwaway `install-check` device is still
  registered. Tell the human, so they can delete it from the app's device list.

If you cannot pair (the gateway CLI is unreachable, for instance), then say plainly in your report
that the roster was **not** verified and that Step 6a's capability check is the only bridge proof
you have. Do not substitute an unauthenticated `curl /bots` for this step.

## Step 8. Remote access (optional, the human's own routing)

The gateway serves plaintext on a LAN. Starting LAN-only is completely fine: the phone and the
gateway on the same network needs nothing further, and the human can add remote access later.

For access from outside the LAN, the routing is the human's, exactly as it is for Hermes desktop's
own remote-gateway story. Two shapes that work:

- **Cloudflare tunnel.** Point a public hostname at the gateway: `cloudflared tunnel route dns
  <tunnel> bots.example.com`, with an ingress rule sending that hostname to
  `http://127.0.0.1:8787` (or `http://gateway:8787` when cloudflared runs as a container on the
  same compose network). WebSockets pass through without extra configuration. The app treats the
  public hostname as a separate gateway entry, so it needs its own pairing code.
- **Tailscale.** Install it on the gateway machine and the phone, then use the machine's tailnet
  address. No public exposure, no certificate work.
- **TLS on the gateway itself.** `docs/tls.md` covers two shipped options: a Caddy sidecar overlay
  that issues its own certificate, or gateway-native TLS from a cert/key pair you supply. Neither
  changes anything you did in this playbook -- the install above sets no TLS variables and the
  gateway it produced serves plain HTTP as documented. Treat TLS as a follow-on the human can ask
  for once pairing works, not a step here.

Do not put the gateway on the open internet without one of these in front of it. This applies
double to the Hermes dashboard if you bound it to `0.0.0.0` in Step 3: it is the human's whole
Hermes control plane behind one password.

## Step 9. Pair the human's phone

Mint the code:

    . ~/cozygateway/local/install-env.sh && cd "$COZY_GATEWAY_DIR" && \
      bash scripts/agent-install.sh --pair-only --gateway-dir "$COZY_GATEWAY_DIR"

or directly:

    . ~/cozygateway/local/install-env.sh && cd "$COZY_GATEWAY_DIR" && \
      docker compose -f docker-compose.yml -f docker/agent-install.override.yml \
      exec -T gateway node dist/cli.js pair --config /app/cozygateway.config.json

Node path:

    . ~/cozygateway/local/install-env.sh && cd "$COZY_GATEWAY_DIR" && \
      node packages/gateway/dist/cli.js pair --config "$COZY_CONFIG_JSON"

**Expect:** one line of JSON (`{"gatewayUrl":"http://127.0.0.1:8787","setupCode":"..."}`) followed
by `Setup code ... is valid for 10 minutes.`

Find the address the phone can actually reach. `ipconfig getifaddr en0` on macOS (try the interface
named by `route -n get default` if `en0` is empty), `hostname -I` on Linux. If neither gives an
address, say you could not determine it and ask the human for their machine's LAN address. Do not
hand them the hostname or `127.0.0.1`: a phone cannot resolve the first or reach the second.

Now **present it to the human**, in exactly this form:

> Your gateway is ready.
>
> - Open CozyChat and add a gateway at **http://192.168.1.50:8787** (your LAN address, or your
>   tunnel hostname).
> - Enter the setup code: **XXXX-XXXX**
>
> The code is single use and expires in 10 minutes. If it lapses, ask me and I will mint another;
> minting is free and unlimited, and old codes simply expire.

**Final check:** after the human pairs, re-run Step 6a and confirm the gateway still answers, then
tell them the install is done, what the roster showed in Step 7 (including "empty, because you have
no bot profiles yet" if that is what it showed), and whether the dashboard is on loopback or on the
LAN.

## Troubleshooting

Every row here is an incident we actually hit.

| Symptom | Cause | Fix |
| --- | --- | --- |
| Step 4b returns **401**, the hash and password look right | A dashboard was already running before the merge. Hermes runs ONE machine-level server by default, and that process is still holding the config it read at startup. `/api/health` answering 200 hides this completely. | `hermes dashboard --stop` (`--status` lists them), then re-run Step 3. The installer restarts it for you; a 401 here means that path was skipped. |
| Gateway logs a **401 on the bridge login**, credentials look right | A `$` in the `.env` value was eaten by compose interpolation; the container received the value truncated at the first `$`. Ours arrived 36 characters long. | Double every `$` in `.env` (`$` becomes `$$`), or regenerate a `$`-free password. Verify with the length comparison in Step 5b. |
| Dashboard **exits immediately** on start, log mentions no auth provider | Hermes fails closed on a non-loopback bind with no auth provider registered. There is no unauthenticated mode and the old `--insecure` flag is a documented no-op. | Complete Step 3, then restart. Or keep the default `127.0.0.1` bind and run the gateway under Node on the same host, which is loopback and needs no LAN exposure. |
| Installer **refuses to merge**: duplicate key `dashboard` | `config.yaml` already had two top-level `dashboard:` keys before this install. `yaml.safe_load` keeps only the last, so merging would silently delete the other block and leave a file whose `grep -c '^dashboard:'` reassuringly prints `1`. | Open the file, fold the two blocks into one by hand, confirm with `grep -n '^dashboard:'`, re-run Step 3. Nothing was written and no backup was taken. |
| Installer **refuses to merge**: `config.yaml` is a symlink | Writing through it would replace the link and retighten the target's mode. | Point `--hermes-home` at the directory holding the real file, or merge by hand. |
| **Comments or anchors vanished** from `config.yaml` | The merge reserializes the whole file through the YAML parser. Values are preserved; formatting, comments and anchors are not. | The original is in `config.yaml.bak-agent-install-*`. Tell the human before they notice. Reapply comments from the backup if they want them. |
| `POST /auth/password-login` returns **404** | The dashboard has no auth provider registered under the name the bridge sent (`basic` by default). | Confirm the human's Hermes bundles `plugins/dashboard_auth/basic`. If they registered a different password provider, add `"provider": "its-name"` to the `hermes` block in the config. The bridge log names the provider it tried. |
| **502 through a tunnel** right after a restart, fine on the LAN | The tunnel reconnected to the origin before the gateway finished starting; the container's healthcheck has a 5s start period and the tunnel does not wait for it. | Wait for `docker compose ps` to show `healthy`, then retry. If it persists, restart cloudflared after the gateway, not before. |
| `/health` answers but has **no `com.cozylabs.bots`** | The mounted config has no `hermes` block: usually the baked default config, not yours. | Confirm the override file is in the `-f` chain and that `local/cozygateway.config.json` exists. `docker compose ... config` shows the resolved mount source. |
| Gateway **exits at startup**: "a gateway must serve something" | The config has neither an agent nor a `hermes` block. | Add the `hermes` block. `"agents": []` alone is not a surface. |
| Gateway **exits at startup**: the passwordEnv variable is unset | The config names an environment variable that never reached the process. Startup fails closed by design rather than advertising a dead bridge. | Confirm `COZYGATEWAY_HERMES_PASSWORD` is in `.env` and that the override file is in the `-f` chain. |
| **Port already in use** on 8787 or 9119 | Another gateway, another dashboard, or an unrelated service. | `lsof -nP -iTCP:8787 -sTCP:LISTEN`. Either stop the other process or move ours: `--gateway-port` / `--dashboard-port`. On the Docker path `--gateway-port` moves the container's port AND the published mapping together (the override file drives both from `COZYGATEWAY_PORT`), so it is safe to use. Moving the dashboard port also rewrites the config's `hermes.url`. |
| `hermes --version` prints a version, but the interpreter has **no `yaml`** | `hermes` is a bash wrapper, so its shebang names a shell and a shebang-based guess falls through to the system `python3`. | Take the interpreter from `hermes --version`'s `Install directory:` line: `<dir>/venv/bin/python3`. Pass it as `COZYGATEWAY_HERMES_PY=... bash scripts/agent-install.sh ...`. |
| Pairing code **rejected as expired or used** | Codes are single use with a 10-minute TTL. | Mint another. There is no limit and no cleanup needed. |
| Step 7 shows `bots:200` with an **empty array** | The human has no Hermes bot profiles yet, or they are all in `hiddenProfiles`. | Not a failure. Check `hiddenProfiles` against the Step 0 answers, then have the human create a bot. |
| A device named **install-check** appears in the app | Step 7's throwaway device was not revoked (its `revoked:` line was not `200`). | Delete it from the app's device list, or `DELETE /devices/<id>` with a paired token. |
| `--service` on Linux: unit installed but **stops after the human logs out** | The user session does not linger, so systemd tears down user services at logout. | `sudo loginctl enable-linger $USER`, then re-run with `--service`. The installer attempts this itself and warns when it fails. |
| `--service` on macOS: **launchd job crashed** and did not come back | `KeepAlive` only restarts a non-zero exit, and `ThrottleInterval` holds it to one restart per 10s; a job that keeps crash-looping inside that window can look stuck. A job stopped by hand (SIGTERM, exit 0) is not restarted at all; that is by design. | `launchctl print gui/$UID/ai.cozylabs.cozygateway` for state and the last exit status; the log named in that output has the real error. Restart by hand with `launchctl kickstart -k gui/$UID/ai.cozylabs.cozygateway`. |
| `--bundle`: install refuses with **bundle sha256 mismatch** | The download was corrupted, interrupted, or the release asset does not match its published hash. `install.sh` refuses to run an unverified bundle on purpose. | Re-download (re-run `curl -fsSL https://cozylabs.ai/install.sh \| bash`, or re-fetch the release asset by hand). If it mismatches repeatedly, treat the asset as possibly tampered and say so before retrying. |

## Appendix A. The stateful half by hand

Only if `scripts/agent-install.sh` cannot run. These commands write the same two state files the
rest of the playbook reads, so each one starts by reading what it needs from a file rather than
from a variable an earlier command set. Run them in order, each as its own command.

**A1. The directory and the state file.**

```sh
mkdir -p ~/cozygateway/local && chmod 700 ~/cozygateway/local && \
umask 077 && cat > ~/cozygateway/local/install-env.sh <<EOF
COZY_GATEWAY_DIR=$HOME/cozygateway
COZY_LOCAL_DIR=$HOME/cozygateway/local
COZY_CONFIG_JSON=$HOME/cozygateway/local/cozygateway.config.json
COZY_ENV_FILE=$HOME/cozygateway/.env
COZY_CRED_FILE=$HOME/cozygateway/local/dashboard-credentials.txt
COZY_GATEWAY_PORT=8787
COZY_DASHBOARD_PORT=9119
COZY_DASHBOARD_HOST=127.0.0.1
COZY_BRIDGE_USER=cozybridge
COZY_RUNTIME=docker
COZY_BUNDLE_PATH=
COZY_NODE=
COZY_HERMES_PY=$(hermes --version | sed -n 's/^Install directory: *//p')/venv/bin/python3
COZY_HERMES_HOME=${HERMES_HOME:-$HOME/.hermes}
COZY_GW_LOG=$HOME/cozygateway/local/cozygateway.log
COZY_DASH_LOG=$HOME/cozygateway/local/hermes-dashboard.log
export COZY_GATEWAY_DIR COZY_LOCAL_DIR COZY_CONFIG_JSON COZY_ENV_FILE COZY_CRED_FILE
export COZY_GATEWAY_PORT COZY_DASHBOARD_PORT COZY_DASHBOARD_HOST COZY_BRIDGE_USER
export COZY_RUNTIME COZY_BUNDLE_PATH COZY_NODE COZY_HERMES_PY COZY_HERMES_HOME COZY_GW_LOG COZY_DASH_LOG
EOF
chmod 600 ~/cozygateway/local/install-env.sh
```

Edit the ports, `COZY_RUNTIME` and `COZY_DASHBOARD_HOST` to match the Step 0 answers before
continuing. `COZY_DASHBOARD_HOST` must be `0.0.0.0` on Docker Desktop or a remote gateway; see the
warning in Step 0. `COZY_BUNDLE_PATH` and `COZY_NODE` are left empty here on purpose: some scripts
that source this file run under `set -u`, and an unset variable there would abort with a bash
error instead of the empty string that honestly means "not the bundle path". Fill them in only if
`COZY_RUNTIME=bundle`.

**Check:** `. ~/cozygateway/local/install-env.sh && "$COZY_HERMES_PY" -c 'import yaml; from plugins.dashboard_auth.basic import hash_password; print("ok")'`
**Expect:** `ok`.

**A2. Generate the password straight into the credentials file.** It is never echoed and never
passed as an argument.

```sh
. ~/cozygateway/local/install-env.sh && umask 077 && \
{ printf 'username=%s\n' "$COZY_BRIDGE_USER"
  printf 'password=%s\n' "$(head -c 256 /dev/urandom | LC_ALL=C tr -dc 'A-Za-z0-9' | cut -c1-32)"
} > "$COZY_CRED_FILE" && chmod 600 "$COZY_CRED_FILE"
```

Bound the source, not the sink. `tr -dc ... </dev/urandom | head -c 32` looks equivalent but kills
`tr` with SIGPIPE, which under `set -o pipefail` aborts whatever shell you are running this in.
Keep `$` out of the password: a `$` inside a compose `.env` value is eaten by interpolation.

**Check:** `. ~/cozygateway/local/install-env.sh && sed -n 's/^password=//p' "$COZY_CRED_FILE" | tr -d '\n' | wc -c`
**Expect:** `32`.

**A3. Hash it with the hasher Hermes bundles**, reading the password from the file and appending
the hash to the same file. Never store a plaintext password in `config.yaml`, and never write your
own hasher: the dashboard verifies against this exact scrypt format.

```sh
. ~/cozygateway/local/install-env.sh && umask 077 && \
COZY_CRED_FILE="$COZY_CRED_FILE" "$COZY_HERMES_PY" - <<'PY'
import os, sys
try:
    from plugins.dashboard_auth.basic import hash_password
except ModuleNotFoundError:
    import hermes_cli
    sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(hermes_cli.__file__))))
    from plugins.dashboard_auth.basic import hash_password
path = os.environ["COZY_CRED_FILE"]
lines = [l for l in open(path).read().splitlines() if l and not l.startswith("password_hash=")]
password = [l.split("=", 1)[1] for l in lines if l.startswith("password=")][0]
lines.append("password_hash=" + hash_password(password))
with open(path, "w") as fh:
    fh.write("\n".join(lines) + "\n")
os.chmod(path, 0o600)
print("hashed")
PY
```

**Check:** `. ~/cozygateway/local/install-env.sh && sed -n 's/^password_hash=//p' "$COZY_CRED_FILE" | head -c 7`
**Expect:** `scrypt$`. A `ModuleNotFoundError: No module named 'plugins'` means `COZY_HERMES_PY` is
wrong; go back to Step 1d. Do not fall back to hashing it some other way.

**A4. Merge it into the existing `dashboard:` block, and pin the approval mode.** Read this
warning before you edit anything.

> **WARNING.** `config.yaml` almost always already has a top-level `dashboard:` key. You must MERGE
> `basic_auth` into that existing block. Appending a second top-level `dashboard:` key produces a
> document whose duplicate key silently discards one of the two blocks, and the failure shows up
> much later as a dashboard that will not start or that ignores your credential. We hit exactly
> this. Do not append. Merge. And refuse to merge at all if the file ALREADY has duplicates, which
> is what the strict loader below is for: without it, the merge would quietly delete one of them
> and `grep -c '^dashboard:'` would then print a reassuring `1`.

```sh
. ~/cozygateway/local/install-env.sh && \
cp "$COZY_HERMES_HOME/config.yaml" "$COZY_HERMES_HOME/config.yaml.bak-$(date +%s)" && \
COZY_CRED_FILE="$COZY_CRED_FILE" COZY_CFG="$COZY_HERMES_HOME/config.yaml" "$COZY_HERMES_PY" - <<'PY'
import os, sys, yaml

class Strict(yaml.SafeLoader):
    pass

def no_dupes(loader, node, deep=False):
    out = {}
    for k, v in node.value:
        key = loader.construct_object(k, deep=deep)
        if key in out:
            raise yaml.YAMLError(f"duplicate key {key!r} at line {k.start_mark.line + 1}")
        out[key] = loader.construct_object(v, deep=deep)
    return out

Strict.add_constructor(yaml.resolver.BaseResolver.DEFAULT_MAPPING_TAG, no_dupes)

path = os.environ["COZY_CFG"]
if os.path.islink(path):
    raise SystemExit(f"{path} is a symlink; refusing to write through it")
try:
    cfg = yaml.load(open(path), Loader=Strict) or {}
except FileNotFoundError:
    cfg = {}
except yaml.YAMLError as exc:
    raise SystemExit(f"refusing to touch {path}: {exc}. Fold duplicate keys by hand first.")
if not isinstance(cfg, dict):
    raise SystemExit(f"{path} is not a YAML mapping; refusing to overwrite it")
creds = dict(l.split("=", 1) for l in open(os.environ["COZY_CRED_FILE"]).read().splitlines() if "=" in l)
dashboard = cfg.get("dashboard") if isinstance(cfg.get("dashboard"), dict) else {}
basic = dashboard.get("basic_auth") if isinstance(dashboard.get("basic_auth"), dict) else {}
basic["username"] = creds["username"]
basic["password_hash"] = creds["password_hash"]
basic.pop("password", None)
dashboard["basic_auth"] = basic
cfg["dashboard"] = dashboard
# The approve/deny pin. `smart` (the 0.20.x default) lets an aux LLM approve a call with no event
# emitted, so the phone is never asked; `manual` is the only mode that always asks a human. Merged
# into whatever `approvals:` block exists, and `timeout` is left alone: it is the human's number,
# and the gateway mirrors it through `hermes.approvalTimeoutSeconds` instead of overriding it.
transport = ((cfg.get("security") or {}).get("approval") or {}).get("transport")
if transport is not None and str(transport) != "builtin":
    raise SystemExit(
        f"{path} sets security.approval.transport: {transport!r}, which routes approvals away "
        "from the dashboard WebSocket. Remove it (or set it to builtin) first; the bridge cannot "
        "see an approval otherwise."
    )
approvals = cfg.get("approvals") if isinstance(cfg.get("approvals"), dict) else {}
approvals["mode"] = "manual"
cfg["approvals"] = approvals
tmp = path + ".tmp"
with open(tmp, "w") as fh:
    yaml.safe_dump(cfg, fh, sort_keys=False, default_flow_style=False)
os.replace(tmp, path)   # write to a tmp file and rename: a crash mid-write must not truncate
os.chmod(path, 0o600)   # the human's config
print("merged")
PY
```

The heredoc terminator `PY` must sit at column 0. If you reindent this block, it will hang waiting
for a terminator it never sees. The merge reserializes the whole file: comments and anchors do not
survive, and the backup you just took is the only copy of them.

Then verify with Step 4.

**A5. Start the dashboard.** `--skip-build` serves the existing web UI instead of building it,
which is what you want in a non-interactive context; drop it if the UI has never been built.

```sh
. ~/cozygateway/local/install-env.sh && cd "$HOME" && \
nohup hermes dashboard --host "$COZY_DASHBOARD_HOST" --port "$COZY_DASHBOARD_PORT" \
```

If a dashboard was already running, stop it first with `hermes dashboard --stop`, or it will keep

**A6. The gateway config**, written by a JSON serializer rather than by hand so a quote in a name
cannot produce an unparseable file:

```sh
. ~/cozygateway/local/install-env.sh && umask 077 && \
COZY_HIDDEN=default "$COZY_HERMES_PY" - > "$COZY_CONFIG_JSON" <<'PY'
import json, os
```

**A7. `.env`, merged rather than rewritten.** The push relay reads `APNS_*` and `COZY_RELAY_PORT`
from this same file, so replacing it wholesale would destroy the human's push configuration.

```sh
. ~/cozygateway/local/install-env.sh && umask 077 && \
COZY_ATTACH="$(head -c 400 /dev/urandom | LC_ALL=C tr -dc 'A-Za-z0-9' | cut -c1-48)" \
"$COZY_HERMES_PY" - <<'PY'
import os
path = os.environ["COZY_ENV_FILE"]
creds = dict(l.split("=", 1) for l in open(os.environ["COZY_CRED_FILE"]).read().splitlines() if "=" in l)
try:
    lines = open(path).read().splitlines()
except FileNotFoundError:
    lines = []
existing = dict(l.split("=", 1) for l in lines if "=" in l and not l.startswith("#"))
owned = {
    "COZYGATEWAY_ATTACH_TOKEN": existing.get("COZYGATEWAY_ATTACH_TOKEN") or os.environ["COZY_ATTACH"],
    # every literal $ doubled, because compose interpolates this file
    "COZYGATEWAY_HERMES_PASSWORD": creds["password"].replace("$", "$$"),
    "COZYGATEWAY_PORT": os.environ["COZY_GATEWAY_PORT"],
}
seen, out = set(), []
for line in lines:
    key = line.split("=", 1)[0].strip() if "=" in line else None
    if key in owned and key not in seen:
        out.append(f"{key}={owned[key]}"); seen.add(key)
    elif key in owned:
        continue
    else:
        out.append(line)
out += [f"{k}={v}" for k, v in owned.items() if k not in seen]
tmp = path + ".tmp"
open(tmp, "w").write("\n".join(out).rstrip("\n") + "\n")
os.chmod(tmp, 0o600)
os.replace(tmp, path)
print("merged .env")
PY
```


Naming `gateway` keeps the optional local relay out of it; hosted push needs no local service. On
